# A9 checkm8 payload addresses and technique

Scope: CPID 0x8000 (s8000 "Maui", Samsung 14nm) and CPID 0x8003 (s8003 "Malta", TSMC 16nm).
Read-only research; no hardware touched, `king.exe` not run.
Reference checkouts made during this task: `research\refs\ipwndfu`, `research\refs\ipwndfu-hd`, `research\refs\gaster`, `research\refs\king-full`.

Label key: **CONFIRMED** = read directly from source at a cited path/URL. **INFERRED** = follows from confirmed facts. **UNCONFIRMED** = not verified.

## Summary — is King wrong, and how?

**King's A9 addresses are NOT wrong.** Every one of the 14 numeric constants King uses for `s8000` is byte-for-byte identical to an independently maintained A9 reference table, and King's `PAYLOAD_DEST` (0x1800E0C00) is additionally reproduced *arithmetically* by an independent implementation that derives it at runtime. King selected the correct payload variant (`checkm8_nopaddingcorruption_arm64`) and the correct payload layout. There is nothing to fix in the address tables.

**King fails for a different reason: its `libusb1_async_ctrl_transfer()`, the primitive that drives every abort/stall step of the exploit, is broken.** The cancellation delay is computed as `double t = timeout / 1000.0` and then compared against a seconds-resolution clock in a busy-wait — so for the 10 µs and 100 µs values King passes, the loop body executes **zero times** and the transfer is cancelled *immediately* after `libusb_submit_transfer()` returns. The Python original busy-waits for real; gaster waits inside `libusb_handle_events_timeout_completed()`. Both of King's stall primitives (`DFU::stall()`, its only cancel-based primitive) and every "async abort" step are therefore degenerate. That failure is silent and total.

Supporting findings:

1. **King's A9 code has never been tested on A9.** The A8-A9 support was contributed as a patch by GitHub user `a1exdandy` (PR pgarba/King#7, "A8-A9 support", merged 2020-02-23). The PR body says *"`S7000` tested on `Linux` … Need to test other devices."* It was tested only on **t7000 (A8, iBoot-1992.0.0.1.19)**. The King README lists S8000/S8003 as supported but contains **no** S8000/S8003 console transcript — every example is `CPID:8010` or `CPID:7000`.
2. **The correct device dispatch is present but cosmetic.** PR#7's `device_platform.py` entry for `cpid=0x8000` has an unbalanced quote (`srtg='"iBoot-2234.0.0.3.3'`), which would be a Python parse error at import. That reinforces that the s8000 path was written, not run. It does not affect the payload, because `exploit_a8_a9()` routes both `CPID:8000` and `CPID:8003` to `payload(0x8003)`.
3. **`checkm8_nopaddingcorruption_arm64` for A9 is CORRECT** — not the bug. It is used for A8/A9 by the a1exdandy patch, by `hack-different/ipwndfu`, by `0x7ff/gaster` (as `payload_A9.S`), and by King. A9/A8 need the "no padding corruption" variant because they take a simpler path than A10/A11: no ROP/JOP callback chain, no WXN patch, and the payload is delivered to directly-executable memory. King's `checkm8()` (A10/A11 path) correctly uses plain `checkm8_arm64`. Swapping them would be the bug.
4. **The libusbK driver is already bound to both DFU nodes** on this host, so the WinUSB silent-reset trap (F009 in `findings.jsonl`) is *not* the current explanation. Verified: both `USB\VID_05AC&PID_1227\CPID:8000_...` and `..._CPID:8003_...` enumerate under class `libusbk devices`, service `libusbK` (libusbK 3.1.0.0, libwdi-autogenerated for `USB\VID_05AC&PID_1227`).
5. King deviates from the reference sequence in two smaller ways (extra `no_leak()`, uninitialised padding buffer, 100 ms vs 10 ms padding timeout). Those are real but secondary; see §3.

**Recommended action:** do not patch King's constants. Either fix `DFU::libusb1_async_ctrl_transfer()` to block in the libusb event loop (mirror gaster's `checkm8_stall()`), or better for a clean-room Rust reimplementation, port gaster's control flow and use gaster's A9 constants — which are derived, not hardcoded.

## 2. Payload source and build process

### 2.1 Two unrelated payload families — do not mix them

| | ipwndfu / King family | gaster family |
|---|---|---|
| A9 shellcode | `bin/checkm8_nopaddingcorruption_arm64.bin` (312 B) | `payload_A9.bin` (280 B) + `payload_handle_checkm8_request.bin` (248 B) |
| A9 handler | `bin/usb_0xA1_2_arm64.bin` (528 B) | same `payload_handle_checkm8_request.bin` |
| Constants count | 8 | 11 |
| A9 extras | none | `ttbr0_vrom_addr`, `patch_addr` (TTBR0 WXN patch) |
| Assembles to | one 912 B blob | one 616 B blob at `PAYLOAD_DEST` + 0x800 B `data` buffer |

gaster's `payload_A9.S` differentially does **more** than `checkm8_nopaddingcorruption_arm64.S`: it clears TTBR0 bits and patches the WXN-immediate at `patch_addr` (`0x10000812C` for both A9s), with `dsb sy; tlbi alle3; isb` around it. The `git diff` between gaster's `payload_notA9.S` and `payload_A9.S` is exactly that TTBR0/WXN block plus one extra `.set` — the diff is 4 insertions / 19 deletions. This is a legitimate design difference, not a bug in either.

### 2.2 gaster's build process (CONFIRMED, `research\refs\gaster\Makefile`)

```make
payload:
	as -arch arm64 payload_A9.S -o payload_A9.o
	gobjcopy -O binary -j .text payload_A9.o payload_A9.bin
	...
libusb:
	xxd -iC payload_A9.bin payload_A9.h
	$(CC) -Wall -Wextra -Wpedantic -DHAVE_LIBUSB gaster.c lzfse.c -o gaster -lusb-1.0 -lcrypto -Os
```

* `.S` sources are committed for **all five** payloads (`payload_A9.S`, `payload_notA9.S`, `payload_notA9_armv7.S`, `payload_handle_checkm8_request.S`, `payload_handle_checkm8_request_armv7.S`).
* The `.bin` blobs are **also** committed, so the `.S` → `.o` → `.bin` step is only needed if you change the source. `as`/`gobjcopy` are macOS tools (`-arch arm64`, `gobjcopy` from binutils). On Linux, equivalently: `aarch64-linux-gnu-as` + `aarch64-linux-gnu-objcopy -O binary -j .text`.
* The `.bin` → `payload_A9.h` step is just `xxd -iC` — a C array. Rust port: `include_bytes!("payload_A9.bin")`.
* Absolute-address constants are **not** in the `.S`; they are placeholders `0x7FFFFFF0..0x7FFFFFFA` resolved by the `.pool` literals, then **overwritten at runtime** by `gaster.c:1108-1134` with the values from the per-device table. So the payload source is device-independent and the address table lives entirely in `gaster.c`.

### 2.3 ipwndfu / King build process

Two stages, and the second is what you actually need:

1. **Blob build** — `ipwndfu-hd/ext/asm/Makefile:46-48` (added by the a1exdandy patch):
   ```make
   xcrun -sdk iphoneos clang src/checkm8_nopaddingcorruption_arm64.S -target arm64-apple-darwin -Wall -o bin/checkm8_nopaddingcorruption_arm64.o
   gobjcopy -O binary -j .text bin/checkm8_nopaddingcorruption_arm64.o bin/checkm8_nopaddingcorruption_arm64.bin
   ```
   Upstream `axi0mX/ipwndfu/Makefile` is identical in shape for its own blobs. **The `.bin` files are committed**, so this is not required to run the tool.
   For a Linux cross-build: `clang --target=aarch64-none-elf -c src/checkm8_nopaddingcorruption_arm64.S -o x.o && llvm-objcopy -O binary -j .text x.o x.bin`.

2. **Blob → delivered payload** — `checkm8.py:149-178` `prepare_shellcode()`. The `.bin` files end with one placeholder word per constant, each initialised to `0xBAD00001 + i` (asserted at build-config time), and `prepare_shellcode()` overwrites those *trailing* words with the per-device values:
   ```python
   placeholders_offset = len(shellcode) - size * len(constants)
   ...
   assert value == 0xBAD00001 + i
   return shellcode[:placeholders_offset] + struct.pack(fmt % len(constants), *constants)
   ```
   King reimplements this verbatim at `main.cpp:179-235`. The placeholder trick is why a **single** `.bin` serves every SoC — including A4 through A11 — and why the same `usb_0xA1_2_arm64.bin` works on A9 and A10 with only `constants_usb_*` swapped.

**Practical answer for a Rust build:** you can `include_bytes!` the committed 312 B / 528 B blobs and overwrite their trailing constant words, exactly as King does. That avoids needing an ARM64 assembler entirely, and the blobs are verified by hash (§1.4). Assembling fresh is only necessary if you want to modify the shellcode.

## 3. The three stages, precisely

Wire primitives, all EP0 control transfers on VID 0x05AC / PID 0x1227. Values below are from `ipwndfu-hd/src/ipwndfu/checkm8.py:181-202` (CONFIRMED), cross-checked against King `src/dfu.cpp:222-243`.

| Primitive | bmRequestType | bRequest | wValue | wIndex | wLength | data | timeout |
|---|---|---|---|---|---|---|---|
| `stall()` | 0x80 | 6 (GET_DESCRIPTOR) | 0x304 | 0x40A | 0xC0 | `'A'×0xC0` | 10 µs, **cancel-based** |
| `leak()` | 0x80 | 6 | 0x304 | 0x40A | 0xC0 (IN) | — | 1 |
| `no_leak()` | 0x80 | 6 | 0x304 | 0x40A | 0xC1 (IN) | — | 1 |
| `usb_req_stall()` | 0x02 | 3 | 0x0000 | 0x80 | 0 | — | 10 |
| `usb_req_leak()` | 0x80 | 6 | 0x304 | 0x40A | 0x40 (IN) | — | 1 |

The asymmetry is the whole point of the exploit: **wLength 0xC1 in `no_leak()` is one byte more than the 0xC0 that the SecureROM's DFU descriptor handler allocated.** The device allocates 0xC0, sees a 0xC1 request, stalls, and leaves a dangling 0xC0-byte buffer. `stall()` is what creates the UAF; `no_leak()` is what grooms the heap around it; `usb_req_leak()` is the 0x40-byte short request that later reads back the freed allocation.

### Stage 1 — heap grooming

**Reference (A8/A9 path, `checkm8.py:910-915`):**
```
stall(device)
leak(device)
for _ in range(40): no_leak(device)
dfu.usb_reset(device)
dfu.release_device(device)
```

**King (`main.cpp:725-732`):**
```
D.stall();
D.usb_req_leak();
for (i = 0; i < 40; i++) D.no_leak();
D.usb_reset();
D.release_device();
```

**Deviation (CONFIRMED):** King emits **41** `no_leak()` operations where the reference emits **40**. The reference's `leak()` (`checkm8.py:185-186`, wLength 0xC0) and `usb_req_leak()` (`checkm8.py:197-198`, wLength 0x40) are *different requests*; King substitutes the latter. Two deviations in one line. Heap-grooming counts are exactly the kind of thing that is tuned, not architectural — but 40 is the only published value.

**Architectural:** one cancel-based abort of a 0xC0 GET_DESCRIPTOR into a 0xC1 request (creates the dangling allocation); a block of `no_leak()` transfers to shape the heap; a device reset to commit the layout.
**Tuning:** the count (40), and whether the preceding transfer is 0xC0 or 0x40.

### Stage 2 — USB setup

**Reference (`checkm8.py:917-922`):**
```
device = dfu.acquire_device()
device.serial_number                                  # force re-read of the string descriptor
libusb1_async_ctrl_transfer(device, 0x21, 1, 0, 0, b"A" * 0x800, 0.0001)   # 100 µs
libusb1_no_error_ctrl_transfer(device, 0, 0, 0, 0, b"A" * 0x500, 10)       # padding, 10 ms
libusb1_no_error_ctrl_transfer(device, 0x21, 4, 0, 0, 0, 0)                # DFU_CLRSTATUS
dfu.release_device(device)
time.sleep(0.5)
```
where `padding = 0x400 + 0x80 + 0x80 = 0x500`.

**King (`main.cpp:735-745`):**
```
D.acquire_device();
D.libusb1_async_ctrl_transfer(0x21, 1, 0, 0, A800, 0.0001);       // same
unsigned char padding[0x500];                                      // UNINITIALISED
D.libusb1_no_error_ctrl_transfer(0, 0, 0, 0, padding, 0x500, 100); // timeout 100, not 10
D.libusb1_no_error_ctrl_transfer(0x21, 4, 0, 0, 0, 0, 0);
D.release_device();
sleep_ms(500);
```

**Deviations (CONFIRMED):**
* Padding buffer is uninitialised stack memory instead of `'A' * 0x500`. Likely harmless (the device reads the request, not the payload) but not what the reference does.
* Padding timeout is **100** where the reference uses **10**. This matters *because* King's async primitive never waits: King's non-blocking 100 ms submit races the immediately following `0x21/4` CLRSTATUS, whereas the reference blocks up to 10 ms and lets the 0x800 A-transfer play out first.

**Architectural:** the 0x800 `0x21/1` DNLOAD issued with a *very short* cancellation budget so the transfer is aborted mid-flight (this is what corrupts the freed object); the padding transfer sized to `0x400 + 2 × 0x80`; the `0x21/4` (DFU_CLRSTATUS) that advances the buffer offset "before triggering the UaF to prevent trashing the heap" (`checkm8.py:855`); the 0.5 s settle.
**Tuning:** exact timeout values, and whether padding is `'A'` or garbage.

### Stage 3 — overwrite + payload

**Reference (`checkm8.py:926-937`):**
```
usb_req_stall(device)                       # 0x2/3, wIndex 0x80, 0 bytes
usb_req_leak(device)                        # ×3
usb_req_leak(device)
usb_req_leak(device)
libusb1_no_error_ctrl_transfer(device, 0, 0, 0, 0, overwrite, 100)
libusb1_no_error_ctrl_transfer(device, 0x21, 1, 0, 0, payload[i:i+0x800], 100)   # per 0x800 chunk
dfu.usb_reset(device)
dfu.release_device(device)
```
with `overwrite = struct.pack('<32xQQ', 0x180380000, 0)` (`checkm8.py:899`) = **48 bytes**: 0x20 zero bytes, then `0x180380000`, then `0`.

**King (`main.cpp:747-770`):** identical, with `uint64_t overwrite[] = {0,0,0,0,0x180380000,0}` — byte-for-byte the same 48 bytes. Then the payload in 0x800 DNLOAD chunks, `usb_reset()`, `release_device()`, 500 ms, re-acquire, check for `PWND:[`.

**No deviation in stage 3.** King's stage 3 is a faithful port.

**Architectural:** the 48-byte overwrite whose `+0x20` word is `LOAD_ADDRESS` (0x180380000) — this is the corrupted `callback` pointer that the ROP-less A9 path consumes; the 6-word width; the 0x800 DNLOAD chunking of the payload; the final reset.
**Tuning:** retry semantics. Note gaster differs substantially here: it loops `checkm8_usb_request_stall() && checkm8_usb_request_leak() && checkm8_no_leak()` until the whole triple succeeds (`gaster.c:901-902`), and it uses a **6-byte** overwrite (`checkm8_overwrite_t.callback.callback = insecure_memory_base`, `gaster.c:1192-1196`) carried on a `0x2/3 wIndex 0x80` request (`gaster.c:1211`) rather than the 48-byte `0x0/0` request. Both are valid; the A9 handoff tolerates either.

### 3.1 Why King's failure is silent — the actual bug

CONFIRMED at `a9lab/king/src/dfu.cpp:262-314`:

```c
auto start = time(nullptr);                                  // 273: whole seconds
...
int i = 0;
int t = (timeout / 1000.0);                                  // 299
while ((time(nullptr) - start) < t) { i++; }                 // 300-303: busy-wait
r = libusb_cancel_transfer(rawRequest);                      // 305
```

`time(nullptr)` has 1-second resolution. For `timeout = 0.0001` (and `0.00001` in `stall()`), `t` is `1e-7`/`1e-8`, and the elapsed whole seconds is `0`. `0 < 1e-7` is **false on entry**, so the busy-wait body never runs and `libusb_cancel_transfer()` fires immediately after `libusb_submit_transfer()` returns.

Compare the two working implementations:

* Python (`checkm8.py:65-83`): `request_timeout = 0` if `timeout < 1`; `start = time.time()` (sub-microsecond); `while time.time() - start < timeout / 1000.0: pass`. For 0.00001 this spins for a real 10 µs.
* gaster (`gaster.c:243-282`): `libusb_fill_control_transfer(..., usb_timeout)` with `usb_timeout = 5` ms default (`gaster.c:1631-1633`), then **blocks in the event loop**:
  ```c
  while(completed == 0 && libusb_handle_events_timeout_completed(NULL, &tv, &completed) == LIBUSB_SUCCESS)
      libusb_cancel_transfer(transfer);
  ```
  with `tv` derived from an `usb_abort_timeout` that starts at `usb_timeout - 1 = 4` ms and is swept across `[usb_abort_timeout_min, usb_timeout]` on each retry (`gaster.c:849-858`, `871-879`). gaster re-issues the cancel on every event-loop tick and retries the whole handshake until the observed transfer length is right.

King's primitive is neither: it does not block in the event loop, and it does not spend any wall time before cancelling. Additionally, King sets `LIBUSB_TRANSFER_FREE_BUFFER` (`dfu.cpp:257`) while `rawRequest`'s buffer is `Request.data()` of a `std::vector` local to the function (`dfu.cpp:275-283`); gaster instead `malloc`s the buffer, keeps it alive across the cancel and frees it explicitly (`gaster.c:250-278`). King's version of the C equivalent of the Python global `never_free_device` (`checkm8.py:20-22, 67`) is not implemented. **INFERRED** that this is an additional hazard; not proven to be the proximate cause.

## 4. A9 vs A10 differences

| | A9 (s8000/s8003) | A10/A11 (t8010/t8011) |
|---|---|---|
| Strip/determine by | CPID 0x8000/0x8003 | CPID 0x8010/0x8011 |
| Entry point | `exploit_a8_a9()` (hack-different) / `checkm8_A8_A9()` (King) | `exploit()` / `checkm8()` |
| Heap grooming | `stall, leak, 40×no_leak, reset` | `stall, hole×no_leak, usb_req_leak, no_leak, reset` — config-driven `hole` (5 or 6) |
| `large_leak` | ignored | present for older SoCs (626–7936) |
| Stage 2 padding | **yes**, `0x400+0x80+0x80` | **no** padding transfer |
| Stage 3 leak count | 3× `usb_req_leak` | 1× (config `leak`) |
| Stage 3 overwrite | 48 B `<32xQQ 0x180380000, 0>` | 0x5xx-byte ROP block with `nop_gadget`s, callback addresses and `0xBEEFBEEF` end marker |
| Payload | `checkm8_nopaddingcorruption_arm64` | `checkm8_arm64` |
| WXN patch | **none** in the ipwndfu/King payload; gaster's `payload_A9` does patch TTBR0/WXN | required: `t8010_t8011_disable_wxn_arm64` |
| ROP / callback chain | **none** — direct execution via the 48-byte overwrite | required: `usb_rop_callbacks()` against `func_gadget` |
| Synchronisation | not needed | `dc civac` / `dmb` / `enter_critical_section` / `write_ttbr0` / `tlbi` ROP chain |
| Payload size limit | 384 + 576 = 912 B (single 0x800 transfer) | 0x400 shellcode + 0x200 handler, then up to 0xC00 B of callbacks |
| Structural constraint | `PAYLOAD_DEST` fixed at `0x1800E0C00` for both A9s | `PAYLOAD_DEST` varies per boot chain (0x1800AFC00, 0x1800B0000, 0x18001BC00) and is a `DeviceConfig` field |

**The load-bearing consequence for a reimplementation:** A9 is *simpler*. gaster's A9 "spray" is a single bounded triple (stall + leak + no-leak) that cannot loop forever; A10/A11 needs a config-driven `hole` count plus a full ROP/JOP chain. Do not port an A10 payload structure to A9, and do not add a WXN/ROP stage to A9 — the 48-byte overwrite with `0x180380000` at `+0x20` is the entire control-flow hijack.

**The most robust A9 stage-2/3 formulation is gaster's**, because it is derived rather than magic:
* padding is `config_overwrite_pad - transfer_ret.sz`, i.e. it *measures* how much the aborted transfer actually wrote and pads to exactly `0x500`. King and ipwndfu hardcode `0x500` and ignore the actual length.
* stage 3's early steps are retried until the observed results match, rather than assumed to succeed once.

## 6. What I could not confirm

* **Whether the s8000 and s8003 SecureROMs genuinely share these symbols.** Both public tables assert they do (gaster has two separate entries with identical values; the ipwndfu table has only the s8003 one). I found no independent dump-based confirmation, and I did not verify either SecureROM's symbol layout. **UNCONFIRMED.** Practical consequence: if the addresses are wrong for one die, they are wrong for that die only — but the evidence available says they are not wrong for either.
* **The precise proximate cause of King's identical failure on both devices.** I confirmed the address tables are correct and confirmed that King's async-abort primitive degenerates to an immediate cancel. I did **not** prove experimentally that this is what kills the exploit — I did not run `king.exe` and did not touch the devices. **INFERRED, strongly.**
* **Whether King's uninitialised padding buffer or the 41st `no_leak()` is independently fatal.** Not determinable without hardware. **UNCONFIRMED.**
* **Whether King's `LIBUSB_TRANSFER_FREE_BUFFER` + local `std::vector` buffer is a real use-after-free** in libusb 1.0.x. It deviates from both working implementations (Python keeps the request in a module global; gaster `malloc`s and frees explicitly) but I did not read the relevant libusb internals. **UNCONFIRMED.**
* **Whether the two devices' actual failure output matches the `Exploit failed! :(` path or an earlier abort.** No console transcript of an A9 King run is stored in `a9lab\findings.jsonl` (which ends at F013, before any exploit attempt). **UNCONFIRMED.**
* **Whether `checkm8_nopaddingcorruption_arm64` alone is sufficient on A9** — i.e. whether the WXN patch that gaster's `payload_A9.S` performs is actually required on A9, or is defensive. Three implementations ship the no-WXN variant for A9, which is evidence it is unnecessary, but I found no explicit statement of why. **UNCONFIRMED.**
* **gaster's A9 support has no published success report I could verify.** Its config table entries for iBoot-2234.0.0.2.22 / .3.3 are the strongest available evidence that those exact addresses are right for these exact firmware builds, but I found no log, issue, or writeup of a successful A9 pwn with gaster. **UNCONFIRMED.**
* I did not examine `checkra1n`, `LukeZGD/gaster`, or `epeth0mus/checkra1n-mod` (surfaced in search, not fetched). One of them may carry an independent A9 table. **Not checked.**
